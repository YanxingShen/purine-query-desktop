# 更新机制设计说明（定稿：①+②+③ 三通道）

## 总览
本软件采用**三通道组合更新**，三者数据源始终是同一份嘌呤数据库（purine-db.json），桌面端为数据管理与密钥签发方，手机端为更新接收方。

| 通道 | 角色 | 适用场景 | 是否需联网 |
|---|---|---|---|
| ① PWA 在线自动更新 | **主通道** | 普通用户日常使用，托管地址更新后打开即自动刷新 | 是 |
| ② 16位短码/二维码受控更新 | 辅通道（默认入口） | 官方分批发布、受控更新、16位短码+托管索引 | 是（拉取索引+更新包） |
| ③ 离线自包含长密钥 | 兜底 | 完全无网络环境，PUR-长密钥内含gzip完整数据库 | 否 |

---

## 通道①：PWA 在线自动更新（主通道）

### 原理
手机端为**在线托管的 PWA**，部署在用户可控的公开静态地址（GitHub Pages / Gitee Pages / 自建 OSS / Vercel / Netlify 等）。
- 应用包含 Service Worker（sw.js），首次访问后缓存全部静态资源（HTML/JS/CSS/数据/图标），可离线使用。
- 当官方将**新版应用 + 新版数据库**推送到托管地址后，用户下次联网打开应用时，Service Worker 检测到资源变更（缓存版本号升级），自动在后台下载新版本，下次启动生效。
- **用户无需任何操作**，打开即更新。

### 边界说明
- 前提：手机端必须部署在公网可访问的 HTTPS 静态地址（PWA 和 Service Worker 要求安全上下文）。
- 自动更新的是**整个应用包**（含前端代码 + 数据库），不是仅数据库。
- 首次更新可能需要关闭并重新打开应用才能生效（SW 标准行为）。
- 若用户长期不联网，将一直使用本地缓存版本。

### 部署方式
将 `web/` 目录全部内容上传到静态托管，确保根路径可访问 `index.html`。托管地址即应用访问地址，也是更新源地址。

## 通道②：16位短码/二维码受控更新（辅通道，默认入口，需联网）

### 原理
桌面端作为**官方签发方**，生成16位短码 `XXXX-XXXX-XXXX-XXXX` 及对应的托管索引文件。手机端输入短码或扫码 → 本地由码算出索引文件名 → 拉取索引 → 两级HMAC验签 → 联网下载更新包 → 校验哈希 → 覆盖本地库/代码。

### 短码格式
- 显示/输入：`XXXX-XXXX-XXXX-XXXX`（4组×4位=16位）
- 字母表：`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（32字母表，剔除易混淆的0/O/1/I）
- 输入大小写不敏感、忽略连字符与空格，统一转大写
- 二维码内容 = 16位码（二维码/扫码属本通道）

### 托管索引文件
- 发版时为每个码生成：`keys/<f>.json`，其中 `f = sha256(码)[:16]`（16位hex）
- 索引文件上传到托管地址的 `keys/` 子目录
- 应用由码本地算出 f，拉取 `BASE/keys/<f>.json?t=时间戳`（BASE=应用自身部署基地址）

### 索引文件内容（完整 token）
```json
{"v":"1.0.4","u":"https://host.com/","h":"sha256...","exp":"2027-12-31","iat":1790535192,"seq":1,"typ":"full","mac":"..."}
```
- `typ`: `data`（仅数据）或 `full`（数据+UI代码一体更新）
- `mac`: 两级 HMAC-SHA256 签名

### 两级 HMAC-SHA256 签名
```
K = sha256(版本盐)
mac = HMAC-SHA256(K, HMAC-SHA256(K, canonical(token除mac)) + '|' + 码)
```

### 设备级一次性
- `used_codes`（存sha256(码)）：同一码本设备二次用 → 拒绝
- `used_types`（存v|类型|h指纹）：同版本同数据二次用 → 拒绝
- 设备清除数据/重装 → 码可再用（"设备初始化不算"）
- **诚实边界**：纯前端无后端，跨设备全局一次性无法强制

### 边界说明
- 二维码只承载16位码，不承载数据；需联网下载索引和更新包
- 主通道① PWA 自动更新仍是推荐的主方案

## 通道③：离线自包含长密钥（兜底，完全离线可用）

### 原理
桌面端生成**离线长密钥**（`PUR-<base64url>` 格式），密钥本身内含 gzip 压缩后的完整数据库 JSON。手机端在通道③ textarea 输入该长密钥后直接解码解压，无需联网。

### 边界说明
- 密钥很长（数百KB），**仅适合复制粘贴，不适合二维码**
- 完全离线可用，无需网络
- 离线包仅更新数据，无法更新UI代码
- 这是彻底离线的兜底方案，日常更新优先使用通道①或②

## 桌面端职责
1. **基础嘌呤查询**：与手机端共用同一数据库和查询逻辑
2. **数据编辑/版本管理**：
   - 浏览、搜索、编辑食物条目（名称/别名/嘌呤值/等级/来源/备注）
   - 新增/删除条目
   - 保存为新版本 JSON 文件（导出下载），自动递增版本号
3. **一次性密钥生成**：
   - 基于当前（或编辑后的）数据库生成通道②密钥（含下载地址）
   - 生成通道③离线包密钥
   - 同时生成密钥二维码
   - 一键复制密钥

## 手机端职责
1. 查询/搜索（含拼音模糊搜索）
2. 分类浏览
3. 每日嘌呤摄入估算
4. 危险分层（BMI）
5. 喝水统计（记录/目标/提醒/柱状图）
6. 尿酸记录（值/日期/备注）
7. 尿酸折线图（周/月/自定义范围，含参考线）
8. 痛风小知识
9. **三种更新通道**：①自动更新提示 ②密钥/扫码更新 ③离线包导入

## 密钥安全机制与真实限制（v1.0.5 起）

### 已实现的安全机制
1. **规范 base64url 编码 + 往返校验**：密钥 payload 用无填充规范 base64url 编码；解码后重新规范编码，必须与输入逐字符相等，否则拒绝。彻底堵死"改末尾字符仍可用"的补位区漏洞。
2. **MAC 签名**：新密钥含 `mac` 字段，mac = sha256(规范token串(不含mac) + 固定盐)。校验时重算比对，不符即拒绝。防止密钥被篡改或伪造。
3. **规范指纹去重**：一次性校验按 token 的规范指纹（v+u/data+h）去重，而非原始输入字符串，杜绝"改字绕过一次性"。
4. **向后兼容**：旧格式密钥（无 mac）仍可用，但必须通过往返校验。

### 真实限制（必须如实告知用户）
1. **纯前端无后端，跨设备全局一次性无法强制**：本方案保证"同设备一次性 + 过期 + 抗篡改"，但无法阻止同一密钥在不同设备上使用。全局一次性需要后端服务支持。
2. **盐值存储在前端代码中**：MAC 签名的盐是固定常量，写在 app.js 里。技术人员可逆向获取盐后自行构造合法密钥。这不是银行级安全机制，其作用是防止普通用户误操作和篡改，而非防止专业逆向。
3. **主通道① PWA 自动更新仍是推荐的主方案**：对于普通用户日常更新，通道①（推送托管地址后自动更新）最安全便捷，无需密钥。
4. **通道②密钥/二维码适用于受控/分批发布场景**，作为辅通道使用。

## 诚实性总声明（UI 中必须展示）
1. 本软件仅供健康参考，不替代专业医疗诊断与治疗建议。
2. 通道①自动更新需将应用部署在公网 HTTPS 静态地址，未部署时仅能使用本地数据。
3. 通道②二维码只承载地址+签名，不承载数据，扫码后需联网下载。
4. 通道③离线包密钥极长，仅适合无网络兜底，不建议日常使用。
5. 密钥验证含规范编码往返校验 + MAC 签名 + 规范指纹去重，但纯前端无后端，跨设备全局一次性无法强制，非银行级安全机制。
6. 嘌呤数据来源于国家卫健委《成人高尿酸血症与痛风食养指南(2024年版)》等公开资料，不同来源数值有出入时已标注范围。
