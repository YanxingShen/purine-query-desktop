# 更新机制设计说明（定稿：①+②+③ 三通道）

## 总览
本软件采用**三通道组合更新**，三者数据源始终是同一份嘌呤数据库（purine-db.json），桌面端为数据管理与密钥签发方，手机端为更新接收方。

| 通道 | 角色 | 适用场景 | 是否需联网 |
|---|---|---|---|
| ① PWA 在线自动更新 | **主通道** | 普通用户日常使用，托管地址更新后打开即自动刷新 | 是 |
| ② 密钥/二维码受控更新 | 辅通道 | 官方分批发布、受控更新、保留"官方发放"仪式感 | 是（拉取更新包） |
| ③ 离线自包含数据包 | 兜底 | 完全无网络环境，密钥本身内含压缩数据 | 否 |

---

## 通道①：PWA 在线自动更新（主通道）

### 原理
手机端为**在线托管的 PWA**，部署在用户可控的公开静态地址（GitHub Pages / Gitee Pages / 自建 OSS / Vercel / Netlify 等）。
- 应用包含 Service Worker（sw.js），首次访问后缓存全部静态资源（HTML/JS/CSS/数据/图标），可离线使用。
- 当官方将**新版应用 + 新版数据库**推送到托管地址后，用户下次联网打开应用时，Service Worker 检测到资源变更（缓存版本号升级），自动在后台下载新版本，下次启动生效。
- **用户无需任何操作**，打开即更新。

### 边界说明
- 前提：手机端必须部署在公网可访问的 HTTPS 静态地址（PWA 和 Service Worker 要求安全上下文）。
- 自动更新的是**整个应用包**（含前端代码 + 数据库），不是仅数据库。
- 首次更新可能需要关闭并重新打开应用才能生效（SW 标准行为）。
- 若用户长期不联网，将一直使用本地缓存版本。

### 部署方式
将 `web/` 目录全部内容上传到静态托管，确保根路径可访问 `index.html`。托管地址即应用访问地址，也是更新源地址。

## 通道②：密钥/二维码受控更新（辅通道）

### 原理
桌面端作为**官方密钥签发方**，生成一次性更新密钥或二维码，内含：更新包地址 + 版本号 + SHA-256 签名 + 有效期。
手机端用户输入密钥或扫码 → 本地验签 → 从指定地址拉取更新包 → 校验哈希 → 覆盖本地数据库。

### 密钥格式
```
PUR-<base64url编码的JSON>
```
解码后的 JSON：
```json
{
  "v": "1.1.0",
  "u": "https://your-cdn.example.com/purine-db-v1.1.0.json",
  "h": "a1b2c3d4...（sha256 十六进制，64字符）",
  "exp": "2027-03-01",
  "notes": "v1.1.0 新增 50 条水产类数据"
}
```
- `v`: 目标数据库版本号
- `u`: 更新包下载地址（静态托管）
- `h`: 更新包的 SHA-256（完整性校验）
- `exp`: 过期日期
- `notes`: 更新说明

### 二维码
桌面端密钥生成器同时生成密钥字符串和对应二维码（QR 码编码同一密钥字符串）。用户可用手机端"扫码更新"功能扫描。

### 手机端更新流程
1. 用户在"我的 → 数据库更新"选择"密钥更新"或"扫码更新"
2. 输入密钥（粘贴）或扫描二维码 → 解码
3. 校验：前缀格式、JSON 合法性、expiry 未过期、版本号大于当前、本设备未使用过
4. 从 `u` 下载更新包 JSON
5. 计算 SHA-256，与 `h` 比对
   - 一致 → 写入 localStorage，更新版本号，标记密钥已使用，刷新数据
   - 不一致 → 拒绝，提示"文件校验失败"

### 边界说明
- **二维码只承载地址+签名 token，不承载数据**。扫码后仍需联网从 `u` 下载更新包。
- 密钥本身不含食物数据，只是"授权令牌"。
- "一次性"是本地约束：已用密钥记录在 localStorage，同设备不可重复用；换设备或清数据后可再用。
- 纯前端无真正服务端鉴权，密钥验证是格式+哈希校验，非银行级安全。
- 前提：更新包地址 `u` 必须公网可访问，且手机端联网。

## 通道③：离线自包含数据包（兜底）

### 原理
对于完全无网络的环境，桌面端可生成**离线数据包密钥**：密钥本身内含 gzip 压缩后的完整数据库 JSON（base64 编码）。手机端输入该密钥后直接解码解压，无需联网。

### 离线包密钥格式
```json
{
  "v": "1.1.0",
  "h": "a1b2c3d4...（解压后数据的 SHA-256）",
  "exp": "2027-03-01",
  "data": "<base64编码的gzip压缩JSON>",
  "notes": "离线更新包 v1.1.0"
}
```
- 无 `u` 字段，有 `data` 字段
- `h` 是解压后原始 JSON 的 SHA-256
- `data` 是 gzip(JSON).toString('base64')

### 边界说明
- 密钥会很长（数据量越大密钥越长，430条约约 200KB → base64 后约 270KB，密钥字符串约 27 万字符），**不适合二维码承载**，仅适合复制粘贴文本。
- 这是彻底离线的兜底方案，日常更新优先使用通道①或②。
- 手机端需支持 gzip 解压（使用 pako 库或 CompressionStream API）。

## 桌面端职责
1. **基础嘌呤查询**：与手机端共用同一数据库和查询逻辑
2. **数据编辑/版本管理**：
   - 浏览、搜索、编辑食物条目（名称/别名/嘌呤值/等级/来源/备注）
   - 新增/删除条目
   - 保存为新版本 JSON 文件（导出下载），自动递增版本号
3. **一次性密钥生成**：
   - 基于当前（或编辑后的）数据库生成通道②密钥（含下载地址）
   - 生成通道③离线包密钥
   - 同时生成密钥二维码
   - 一键复制密钥

## 手机端职责
1. 查询/搜索（含拼音模糊搜索）
2. 分类浏览
3. 每日嘌呤摄入估算
4. 危险分层（BMI）
5. 喝水统计（记录/目标/提醒/柱状图）
6. 尿酸记录（值/日期/备注）
7. 尿酸折线图（周/月/自定义范围，含参考线）
8. 痛风小知识
9. **三种更新通道**：①自动更新提示 ②密钥/扫码更新 ③离线包导入

## 诚实性总声明（UI 中必须展示）
1. 本软件仅供健康参考，不替代专业医疗诊断与治疗建议。
2. 通道①自动更新需将应用部署在公网 HTTPS 静态地址，未部署时仅能使用本地数据。
3. 通道②二维码只承载地址+签名，不承载数据，扫码后需联网下载。
4. 通道③离线包密钥极长，仅适合无网络兜底，不建议日常使用。
5. 密钥验证为本地格式+哈希校验，非银行级安全机制。
6. 嘌呤数据来源于国家卫健委《成人高尿酸血症与痛风食养指南(2024年版)》等公开资料，不同来源数值有出入时已标注范围。
